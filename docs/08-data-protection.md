# 08 — Data Protection & Demo Data Policy

**Status:** in force
**Applies to:** everything in this repository, every branch, every commit
**Owner:** repository owner

---

## 1. The rule

> No data that identifies a customer, a member of staff, a shipment or a bank
> account may be committed to this repository.

This applies to the application source, fixtures, tests, documentation, commit
messages, branch names, issue titles and pull request descriptions. It applies
to files deleted in a later commit, because git keeps them.

There is no exception for "temporarily", "only on a branch", or "it is just one
record".

The repository holds **demo data only**, and does so by design rather than by
periodic cleanup. Everything below exists to keep that true.

---

## 2. What the repository holds

### 2.1 Customer master — 1,892 fictional companies

Generated by [`tools/generate-customers.py`](../tools/generate-customers.py)
into `fixtures/customers.demo.json`, which is embedded in the application
as the `CUSTOMERS` array.

The generator is self-contained: every value is invented, and every proportion
is a constant declared at the top of the file. It takes no input.

Every customer has a fake tax registration number and a full address, so any
customer chosen as a billing party shows both on the advice, and both the AWB owner and billing party pickers list exactly these customers -
never names held in a browser's saved data from earlier use. Contact details stay patchy - some
customers have no landline, mobile or email - and telephone numbers are formatted
inconsistently, so the application is still exercised against untidy data.

Seeded with a fixed value, so the dataset is reproducible by anyone and diffs
stay reviewable. CI regenerates it and fails if the committed file differs,
which prevents anyone hand-editing values into it.

Regenerate with:

```bash
npm run customers
```

Note that this does **not** update the copy embedded in
`app/solitair-invoicing.html` — replace the `CUSTOMERS` array there in the same
change.

### 2.2 Safe by construction

| Field | Convention | Why it is safe |
|---|---|---|
| Email domains | `<name>.example` | `.example` is reserved by RFC 2606 and IANA for documentation. It can never be delegated and can never resolve to a mailbox. |
| Telephone numbers | contain `555` | The long-standing fictional-number convention. |
| Company names | coined from syllable pools | Assembled from invented syllables, compared on letters and digits only so punctuation cannot mask a duplicate. |
| Tax registration numbers | random, unique digits in the UAE 15-digit format, one per customer | Generated, never entered. |
| Addresses, cities and states | curated tables, chosen by country | Fixed lists in the generator; every customer has one. |
| Air waybill numbers | `780-3090xxxx` in the demo seed and fixtures | A reserved demo band. Test specs use their own invented sequential ranges. |
| Demo shipments | `shDemoItems()`: AWBs `780-30901001` to `780-30901010`, flights `ZZ 901` to `ZZ 910` | Generated inside the application; owners are drawn from the demo master. |

### 2.3 Staff

Counter staff in the repository are `Counter 1` … `Counter 6`. Names are entered
on the counter machine under **Rates & Data → Counter Staff** and stored in that
browser only.

### 2.4 Company and bank details

`CFG.company.trn` and the whole of `CFG.bank` are the string `"Not configured"`
in source. They are **site configuration, not code**.

Values are entered once per counter machine under
**Rates & Data → Company & Bank Details**, saved to that browser's
`localStorage` (`DB.company`, `DB.bank`), and re-applied at boot by
`applySiteOverrides()`. Nothing writes them back to the application file, so
they cannot reach source control.

This is the same override pattern already used for tariff rates, free-storage
hours and the staff list.

> **Operational consequence.** A freshly cloned copy of the application prints
> `Not configured` where the TRN and bank blocks belong. That is correct and
> intended. Configure it before use — see
> [`06-operations-runbook.md`](06-operations-runbook.md) section 0.

### 2.5 The tariff

The commercial tariff in `EXPORT_LINES` / `IMPORT_LINES` is genuine. It is
confidential business information but it is not personal data, and the
application cannot function without it. It is the main reason this repository
stays private.

## 3. Controls

### 3.1 Automated — `tools/pii-scan.js`

Runs in CI on every push and pull request, and locally:

```bash
npm run scan
```

Five structural rules, applied to every text file in the repository:

| Rule | Fails on |
|---|---|
| `email-outside-reserved-tld` | Any email address whose domain is not `.example` |
| `uae-iban` | Anything matching `AE` + 21 digits |
| `bic-swift` | Anything matching a UAE BIC/SWIFT code |
| `uae-phone-not-fictional` | Any `+971` number that does not contain `555` |
| `trn-not-in-demo-master` | Any 15-digit number not present in the demo master |

**The scanner holds no denylist and no hashes.** A 15-digit tax number has a
small enough search space that publishing its hash would effectively publish the
number. Every rule recognises the *shape* of live data instead, so the guard
carries nothing sensitive itself.

### 3.2 Automated — generator reproducibility

CI regenerates the demo master and fails if the committed file differs.

### 3.3 Automated — backup files

CI fails if any `*.backup.json` or `data/` file, or any `.csv`, `.tsv`, `.xlsx` or
`.xls` file, is committed. Backups are `localStorage` exports from a counter
machine and contain live invoices; spreadsheets and CSVs are how shipment
manifests arrive, and manifests name customers and shipments. `.gitignore` blocks
all of them.

### 3.4 Procedural — tests

Test specs must never contain a literal customer name. They use
`h.SAMPLE_CUSTOMER` and `h.OTHER_CUSTOMER`, resolved from the demo master by
`tests/harness.js`. A spec therefore cannot introduce a customer name at all,
and the suite keeps working when the master is regenerated.

### 3.5 Procedural — repository visibility

**This repository must remain private.** See section 2.5.

## 4. Working with live data

Live data lives in exactly three places, and none of them is this repository:

1. **The counter machine's browser storage.** This is the system of record.
2. **The end-of-shift JSON backup**, taken under Rates & Data → Download Backup.
3. **Shipment manifests**: the Excel or CSV files pasted into the Shipment
   Database, and the shipments loaded from them.

Treat all three as confidential business records:

- Store backups on company-controlled storage. Not personal cloud accounts, not
  email, not chat.
- Never attach one to an issue or a pull request.
- Never paste customer records, bank details or tariff figures into a
  third-party tool, including AI assistants.
- To reproduce a customer-specific bug, describe the *shape* of the data, or
  reproduce it against a demo record with the same characteristics.
- To test the Shipment Database, use the sample shipments it opens with (**Load Sample Shipments** reloads them), or build a manifest
  from demo customers as `tests/specs/10-awb-first.spec.js` does. Never a real
  manifest, and never a screenshot of one.

### Customer details

The application runs on the demo master, shown on the Customer Database tab. A
backup holds customer **names** only, so restoring one never brings TRNs or
addresses with it. By decision there is no way to load a real customer master
into this prototype: the real master, with its TRNs and addresses, belongs in the
ERP (`09-governance.md` D-11).

## 5. If live data is committed

Treat it as a data incident, not a routine mistake.

1. **Do not simply commit a deletion.** Git retains the content, and if the
   commit was pushed, so does the remote.
2. Confirm the repository is private.
3. Rewrite history to remove the blob (`git filter-repo` or BFG), then
   force-push. Every clone must be re-cloned; old clones still hold the data.
4. If bank account details were exposed, treat the accounts as disclosed and
   consult Finance.
5. Record what was exposed, for how long, and to whom — **in the incident
   record, not in this repository.**
6. Add a `tools/pii-scan.js` rule that would have caught it.

> Note step 5. Descriptions of an exposure are themselves sensitive: volumes,
> field coverage and record counts all describe the customer base. Incident
> detail belongs in the incident record, never in documentation, a commit
> message or a changelog entry.

## 6. For the ERP vendor

When this system is replaced, these are the properties the replacement should
carry forward:

| Requirement | Rationale |
|---|---|
| Customer personal data must not live in application source or configuration | It is counterparty data with no business reason to be in a build artefact |
| Bank and tax details must be environment configuration, not code | They differ per entity and change without a release |
| Non-production environments must use generated or masked data | Demo, training and test environments are the usual leak path |
| Test data must be generated and reproducible, not a copy of production | A copy is a second production database with weaker controls |
| An automated check must gate the pipeline | Policy that is not enforced decays |
| Master-data import must validate | A field that accepts anything will eventually carry the wrong thing onto a printed document |

The relevant obligations are in UAE Federal Decree-Law No. 45 of 2021 on the
Protection of Personal Data. This document is an engineering control record, not
a legal assessment; confirm the compliance position with whoever owns it.
